## Schema and compatibility

- New bookings require `schemaVersion: 2`, a 64-character request fingerprint, namespaced UUID ID, `scheduleAt` and authoritative quote snapshots. Historical bookings are not recalculated or rewritten; permitted legacy workflow transitions continue. Completed care never marks cash paid.
- `reportReceipts/{reportId}` contains only booking ID, reporter UID, reporter-submitted reason, status and timestamp. `reportLocks/{bookingId}` records one original report ID/reporter. Both are separate from private moderator documents. New reporter writes cannot alter locks or moderation status.
- Category `household` maps to `vendor`. Existing valid IDs remain stable. Unknown labels or multiple possible service matches require reviewed mapping; no service/ownership guess is applied.
- Private caregiver `allowZeroRate: true` is required for an intentional zero price. Migration never infers free pricing. Organization commission `0` remains valid; absent legacy commission defaults to 15 consistently. Public listing quote fields are not an authorization source.
- Approval operation IDs belong to server operations and prevent unrelated/concurrent safety changes being undone by rollback. They are not permission grants.
- Indexes retain existing public filters and add booking organization/status, organization/status/totalAmount, organization/status/vendorEarnings and caregiver/customer status combinations. Keep existing indexes during rollout; emulator success does not prove production indexes have finished building.

## Safe migration and rollback rehearsal

`scripts/migration-plan.cjs` is a pure planner. `scripts/migrate-demo.cjs` defaults to a dry run over a local export shaped as `{ "collection/documentId": { ...fields } }`. Represent timestamps as `{ "__timestamp": "2026-01-01T00:00:00.000Z" }`. Exports, plans and journals can contain private data: keep them in the ignored `.local-tools` directory or an operator-controlled secure directory, never Git.

```powershell
node scripts/migrate-demo.cjs --dry-run .local-tools/reviewed-export.json > .local-tools/migration-plan.json
```

Review every `blocked` item and every before/after value. The planner preserves original report documents, creates canonical private copies for valid `caregiverReports`, emits safe receipts under original IDs and a booking lock, and converts only canonicalizable categories/service references. It never changes roles, claims, booking amounts or safety decisions. Rerunning against the resulting data produces no new changes.

Apply and rollback are deliberately **demo-only**. Start the demo emulator using `firebase.test.json` and project `demo-sewak-test`, load the exact reviewed records into it, and keep that same emulator running for both operations. In a separate terminal pointing at it:

```powershell
$env:GCLOUD_PROJECT = 'demo-sewak-test'
$env:FIRESTORE_EMULATOR_HOST = '127.0.0.1:8080'
node scripts/migrate-demo.cjs --apply-demo .local-tools/reviewed-export.json .local-tools/migration-journal.json
node scripts/migrate-demo.cjs --rollback-demo .local-tools/migration-journal.json
```

Use a persistently imported/exported emulator dataset for manual rehearsal; a fresh `emulators:exec` instance without data cannot satisfy before-state checks. The ordinary test runner intentionally starts fresh; its backend migration test seeds synthetic records and verifies apply, conflicting rollback rejection and clean rollback in one session. Apply writes an exclusive journal before mutations, compares each live before-state transactionally, and stops on conflicts. Rollback compares the expected after-state before restoring; it never overwrites an intervening moderation/safety/profile change. An interrupted apply can be rolled back using its prewritten journal. A rollback of report compatibility records is only appropriate while the new report writer is paused.

This script cannot apply to production. A production export, explicit mapping of blocked records, backup, and separately authorized operator migration are prerequisites; none were performed. Do not simply remove the guard. Reuse the reviewed pure plan through the organization's authorized migration process.

## Remaining environment limits and risks

- No deployment or production-data verification was authorized or performed. Actual canonical origin, Cloudflare dashboard rules, deployed index readiness, custom-claim inventory and real App Check token transport are pending authorized environment checks. This is a tested implementation, not a claim of production rollout.
- Firebase Hosting is declared locally; no Cloudflare Worker backend manifest is present. The frontend remains a static SPA. Served public metadata is generic and canonicalizes to `/browse`; caregiver-specific metadata is browser-rendered. Unknown client routes show NotFound but SPA fallback returns HTTP 200. Dynamic crawler/social metadata and real HTTP 404 behavior need a separately scoped host rendering/routing integration.
- Trial service publication is atomic and safe. Automatic caregiver/review projection refresh and privileged account/safety operations rely on already-available Functions; no paid service has been introduced. If unavailable, caregiver public updates require the constrained superadmin publisher, and privileged operations stay blocked. Stale public availability can affect presentation but cannot bypass private booking checks.
- Legacy report records with unverifiable ownership/status/timestamps or ID collisions stay private and appear in the dry-run blocked list. Live migration is not presumed complete. Legacy unknown monetary values are displayed as recorded/missing rather than reconstructed.
- New organization applications remain customers until reviewed approval. Invitation link generation is not proof of email delivery. No real email/SMS delivery, physical mobile devices, accessibility screen-reader session or real-user Web Vitals measurement was performed.
- Web Locks protect same-origin cross-tab attempt creation in supported secure-context browsers. The fallback serializes a single page; retries sharing an existing attempt are still transactional. Different browser profiles/devices intentionally hold different attempts. Storage failure prevents submission rather than silently losing the idempotency key.
- Root tooling is legacy CRA, and the host test Node version differs from the declared Functions Node 20 runtime. Existing dependency audit warnings were not mass-fixed: such upgrades require separate compatibility review. Large superadmin/customer histories still load for exact existing search/filter/global counts; organization pagination and shared customer subscriptions are targeted improvements, not a wholesale dashboard rewrite.

Security rules received an adversarial review using the repository Firebase security-rules-auditor skill. The machine-readable assessment is in `firestore-security-review.json`; local tests are evidence for the scoped changes, not an independent security certification.
