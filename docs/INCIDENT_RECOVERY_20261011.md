# Single-incident recovery: 2026-10-11 sewak-final authentication outage

**Not a routine deployment method.** Normal `npm run deploy:cloudflare` **continues to require passing pre-deployment Auth QA** and remains unchanged. This is a one-time recovery from the known bad deployed version `750f1bb7-7bfd-43a8-89d2-f87cb90ab9c6`, which fails synthetic registration with `delivery-unavailable` and returns 503 for login and invalid session cookies.

The special operator checks the **exact active Worker version**, pinned account and both D1 bindings, production write-enabled config, clean and up-to-date GitHub main (containing the diagnostic fix), all offline build/type/lint/unit/D1 checks, a guarded Worker dry-run, a clean release scan, fresh remote database integrity results, Workers Free plan, and **D1 Time Travel recovery bookmarks for both databases**. During execution it requires fresh synthetic QA failure evidence with **verified cleanup** tied to the bad version. A typed confirmation is mandatory.

1. Confirm there are no unintended production changes and that Cloudflare Time Travel is available. Do not restore either D1 database automatically: rewinding could destroy legitimate customer bookings made after the bookmarked time.
2. In a **clean** `Sewak-clean-release` checkout, run `git pull --ff-only origin main`, set `CLOUDFLARE_ACCOUNT_ID` to the Sewak account, run `npm ci` and `npm --prefix worker ci` if dependencies are missing, then `node scripts/incident-recover-sewak-final.mjs --prepare`. This may take several minutes but **does not deploy** or mutate D1.
3. Set `SEWAK_QA_GMAIL` to a Gmail inbox the operator controls. Run `node scripts/verify-cloudflare-auth.mjs --worker sewak-final --apply-synthetic-qa --verify-write-enabled-production` to generate a fresh failing report and verify cleanup. **Stop if cleanup fails**. This operation runs controlled synthetic test records and requires consent.
4. Only after reviewing the report, run `node scripts/incident-recover-sewak-final.mjs --execute --failed-qa .local-tools/cloudflare-auth/sewak-final-qa-<NEW-ID>.json`, then type `RECOVER sewak-final 750f1bb7` to authorize the one-time upload. This requires a fresh prepared report, matching deployed version, exact failure mode, passing and recent D1 validation, and full release tests.
5. The operator deploys the already packaged repo revision with reviewed production bindings, checks public caregiver search, health, and invalid-session handling, then reruns **fresh production D1 checks and full synthetic Auth QA** (including browser sign-in). If any post-deploy check fails, it attempts **Worker-code rollback only** to the prior pinned version. The operator does **not** restore D1 or delete any customer records. Check rollback status and investigate failed cleanup before any retry.
6. After full success, manually inspect existing customer/caregiver/organization login, booking, ratings, and responsive layout. Do not assume synthetic QA proves every existing account works. The old Worker code may have produced credential hashes incompatible with the new implementation; if existing-user login fails, diagnose compatibility rather than resetting all accounts.

Never use this exception for another Worker version, database, user account, or failure mode. Cloudflare's normal historical rollout and D1 restore procedures remain separate.

## Deployment readiness

An October 11 attempt uploaded version `9e3b6141-7769-4e78-84cf-72b6343e8998` but failed an immediate post-upload check before synthetic QA. Subsequent read-only probes of that version passed health, anonymous auth, invalid-cookie 401 and public browsing. The reviewed code-only rollback completed. This supports a deployment-readiness race; the original script did not expose the failed phase, so the exact assertion is unconfirmed.

The recovery now waits for a single new version at 100% and passing existing binding/smoke assertions. Only the prior pinned version still appearing in deployment metadata or explicit HTTP 503 smoke responses are retryable, with at most 15 attempts and two-second gaps. Wrong status codes, malformed success payloads, mixed deployments, binding/security failures and full Auth QA failures remain fatal. A persistent 503 still rolls back. Logs contain fixed phase/stage labels and finite categories, never raw exceptions or private request values. Automatic code rollback uses Wrangler's `--yes` so it cannot stall at an additional interactive prompt; the initial recovery authorization prompt remains intact.
